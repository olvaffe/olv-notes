# Kernel cgroup

## Overview

- `cgroup.c`
  - `struct cgroup_root` represents a cgroup hierarchy
    - there is a single hierarchy, `cgrp_dfl_root`, in v2
  - `struct cgroup` represents a cgroup
    - there is a `struct cgroup` embedded in `struct cgroup_root`
  - `struct css_set` represents the state of a cgroup
    - there is 1:1 between `struct cgroup` and `struct css_set` in v2
    - `find_css_set` allocs `css_set` on demand
    - `init_css_set.dfl_cgrp` points to `cgrp_dfl_root.cgrp`
  - `init_task` belongs to the root cgroup
    - `init_task.cgroups` points to `init_css_set`
- `rstat.c`
  - after a stat is updated, `css_rstat_updated` adds `css->rstat_cpu` to
    `ss->lhead` to mark it dirty
  - before a stat is read, `css_rstat_flush` folds the per-cpu counters into
    the cgroup counter
    - `css_rstat_updated_list`
      - `css_process_update_tree` builds an update tree from `ss->lhead` list
      - it flattens the update tree to an ordered list
    - `cgroup_base_stat_flush` folds the stat
- `namespace.c`
  - `copy_cgroup_ns` returns the old cgroup ns or allocs a new one depending
    on `CLONE_NEWCGROUP`
    - the new cgroup ns treats the task's cgroup as the root cgroup
- `freezer.c`
  - when userspace writes to `cgroup.freeze`, `cgroup_freeze` freezes all
    processes in the cgroup hierarchy

## Userspace

- <https://docs.kernel.org/admin-guide/cgroup-v2.html>
- Introduction
  - Terminology
    - singular "cgroup" refers to the whole feature
    - plural "cgroups" refers to individual control groups
  - What is cgroup?
    - cgroups form a tree
    - every process belongs to one and only one cgroup
    - controllers may be selectively enabled/disabled on a cgroup
- Basic Operations
  - Mounting
    - `mount -t cgroup2 none /sys/fs/cgroup`
  - Organizing Processes and Threads
    - initially only root cgroup exists and all processes belong to the root
      cgroup
    - to create a child subgroup, `mkdir $CHILD`
    - to look up between cgroup and process,
      - `cat /proc/$PID/cgroup` shows the cgroup
      - `cat /sys/fs/cgroup/$CHILD/cgroup.procs` shows all processes
  - [Un]populated Notification
    - `cgroup.events`
  - Controlling Controllers
    - `cgroup.controllers` lists available controllers
    - `cgroup.subtree_control` configs/lists enabled controllers
    - when controller `foo` is enabled for `$PARENT`, `$PARENT/$CHILD/foo.*`
      are created
    - top-down constraint
      - resources are distributed top-down
      - a cgroup can further distribute a resources only when its parent has
        distributed the resource to it
    - No Internal Process Constraint
      - either `cgroup.procs` or `cgroup.subtree_control` must be empty
      - iow, processes must belong to leaf cgroups
      - unless root cgroup, because kthreads belong to the root cgroup
      - this does not apply to "threaded" cgroups, where `cgroup.type` is
        `threaded`
  - Delegation
  - Guidelines
    - avoid migrating processes between cgroups, which is expensive
    - avoid name collision with core `cgroup.*` and controller `foo.*`
- Resource Distribution Models
  - Weights
    - range `[1, 10000]`, default 100

  - Limits
    - range `[0, max]`, default max

  - Protections
    - range `[0, max]`, default 0

## Available Controllers

- `include/linux/cgroup_subsys.h`
  - explicit (`.dfl_cftypes`)
    - `CONFIG_CPUSETS` and `cpuset_cgrp_subsys`
    - `CONFIG_CGROUP_SCHED` and `cpu_cgrp_subsys`
    - `CONFIG_BLK_CGROUP` and `io_cgrp_subsys`
    - `CONFIG_MEMCG` and `memory_cgrp_subsys`
    - `CONFIG_CGROUP_HUGETLB` and `hugetlb_cgrp_subsys`
    - `CONFIG_CGROUP_PIDS` and `pids_cgrp_subsys`
    - `CONFIG_CGROUP_RDMA` and `rdma_cgrp_subsys`
    - `CONFIG_CGROUP_MISC` and `misc_cgrp_subsys`
    - `CONFIG_CGROUP_DMEM` and `dmem_cgrp_subsys`
  - implicit (`.implicit_on_dfl`)
    - `CONFIG_CGROUP_PERF` and `perf_event_cgrp_subsys`
    - `CONFIG_CGROUP_DEBUG` and `debug_cgrp_subsys`
  - legacy
    - `CONFIG_CGROUP_CPUACCT` and `cpuacct_cgrp_subsys`
    - `CONFIG_CGROUP_DEVICE` and `devices_cgrp_subsys`
    - `CONFIG_CGROUP_FREEZER` and `freezer_cgrp_subsys`
    - `CONFIG_CGROUP_NET_CLASSID` and `net_cls_cgrp_subsys`
    - `CONFIG_CGROUP_NET_PRIO` and `net_prio_cgrp_subsys`
- `CONFIG_CPUSETS` regulates cpu cores and numa memory nodes
  - `cpuset.cpus` sets/shows non-hierarchical local allowed cpus
  - `cpuset.cpus.effective` shows effective allowed cpus
    - this takes both the hierarchy and the online status into consideration
  - `cpuset.mems` sets/shows non-hierarchical local allowed numa memory nodes
  - `cpuset.mems.effective` shows effective allowed numa memory nodes
  - `cpuset.cpus.partition` sets/shows partitioning
    - say parent cgroup allows cpu 0-7 and child cgroup allows cpu 4-7
    - `member` on child means parent effective allowed cpus are cpu 0-7
    - `root` on child means parent effective allowed cpus are cpu 0-3
    - `isolated` is similar to `root` and futhermore disables load balancing
      and housekeeping
      - even an isolated cpu is completely idle, sched does not move tasks on
        other cpus or housekeeping tasks to the isolated cpu
  - `cpuset.cpus.isolated` shows isolated cpus
  - `cpuset.cpus.exclusive` sets/shows non-hierarchical local exclusive cpus
    - when a child uses `root` partition, it carves out cpus from the parent
    - when if we want a grandchild uses `root` partition?
      - we use `exclusive` along its ancestor chain
- `CONFIG_CGROUP_SCHED` regulates cpu time
  - `CONFIG_GROUP_SCHED_WEIGHT`
    - `cpu.weight` sets/shows weight (`[1, 10000]`)
      - sched allocs cpu times to cgroups based on weights
    - `cpu.weight.nice` sets/shows weight  (`[-20, 19]`)
      - same as `cpu.weight`, except it maps nice vals to raw weights
    - `cpu.idle` sets/shows whether the cgroup is idle
      - it is similar to `SCHED_IDLE`, but is relative to sibling cgroups
  - `CONFIG_GROUP_SCHED_BANDWIDTH`
    - `cpu.max` sets/shows max cpu time
      - it sets both quota and period
    - `cpu.max.burst` sets/shows burst cpu time
      - it allows burst in a period when there is remaining quota from prior
        period
  - `CONFIG_UCLAMP_TASK_GROUP`
    - `cpu.uclamp.min` sets/shows min uclamp
      - sched calculates cpu utilization (`util_avg`) and
        - feed it to `schedutil` for cpufreq
        - move tasks between big/little cores
      - `util_avg` is clamped to `[cpu.uclamp.min, cpu.uclamp.max]`
    - `cpu.uclamp.max` sets/shows max uclamp
- `CONFIG_BLK_CGROUP` regulates block io
  - `io.stat` shows stats of all block devs
  - `CONFIG_BLK_CGROUP_IOPRIO`
    - `io.prio.class` sets/shows prio class assigned to bios
      - by default, kernel uses `none` for mq hw (nvme) or `mq-deadline` for
        non-mq hw
      - the prio class is translated to hw class or handled by `mq-deadline`
  - `CONFIG_BLK_DEV_THROTTLING`
    - `io.max` sets/shows max bandwidths
  - `CONFIG_BLK_CGROUP_IOCOST`
    - `io.cost.qos` sets/shows qos
      - it enables/disables/tunes iocost policy
      - iocost policy is better than max bandwidths to estimate the real costs
    - `io.cost.model` sets/shows cost model
    - `io.weight` sets/shows weight
      - it allocates device times to cgroups based on weights
  - `CONFIG_BFQ_GROUP_IOSCHED`
    - `io.bfq.weight` sets/shows weight
      - it replaces `io.weight` when bfq is used
  - `CONFIG_BLK_CGROUP_IOLATENCY` is experimental
    - `io.latency` sets/shows guaranteed latency
- `CONFIG_MEMCG` regulates memory usage
  - `memory.current` shows current usage
  - `memory.peak` shows historical peak usage
  - `memory.min` sets/shows min usage
    - never reclaim if below min
  - `memory.low` sets/shows low usage
    - reclaim last if below low
  - `memory.high` sets/shows high usage
    - sched reclaim after alloc if above high
      - the return-to-userspace path waits for the reclaim
      - if reclaim fails, throttles (sleeps) but never oom kills
    - userspace oomd should react to this
  - `memory.max` sets/shows max usage
    - force direct reclaim before alloc if above max
      - if reclaim fails, oom kills
    - last resort when userspace oomd does not react to `memory.high`
  - `memory.events` shows event counts
    - `MEMCG_LOW`
    - `MEMCG_HIGH`
    - `MEMCG_MAX`
    - `MEMCG_OOM`
    - `MEMCG_OOM_KILL`
    - `MEMCG_OOM_GROUP_KILL`
    - `MEMCG_SOCK_THROTTLED`
  - `memory.events.local` shows non-hierarchical local event counts
  - `memory.stat` shows stats
  - `memory.numa_stat` shows stats by numa nodes
  - `memory.oom.group` sets/shows oom group
    - when a task is oom-killed, this controls whether other tasks in the
      cgroup are killed
  - `memory.reclaim` triggers reclaim immediately
  - `CONFIG_SWAP`
    - `memory.swap.current` shows current usage
    - `memory.swap.peak` shows historical peak usage
    - `memory.swap.high` sets/shows high usage
      - throttle mem alloc if above high
      - userspace oomd should react to this
    - `memory.swap.max` sets/shows max usage
      - never use more than max swap space
    - `memory.swap.events` shows event counts
      - `MEMCG_SWAP_HIGH`
      - `MEMCG_SWAP_MAX`
      - `MEMCG_SWAP_FAIL`
- `CONFIG_CGROUP_HUGETLB` regulates hugetlb usage
  - hugetlb calls
    - `hugetlb_cgroup_charge_cgroup` to charge allocs
    - `hugetlb_cgroup_uncharge_cgroup` to uncharge allocs
    - `hugetlb_cgroup_charge_cgroup_rsvd` to charge mmaps and allocs
    - `hugetlb_cgroup_uncharge_cgroup_rsvd` to uncharge mmaps and allocs
  - `hugetlb.<hugepagesize>.numa_stat` shows current alloc sizes by nodes
  - `hugetlb.<hugepagesize>.current` shows current alloc size
  - `hugetlb.<hugepagesize>.rsvd.current` shows current resv size
  - `hugetlb.<hugepagesize>.max` sets/shows max alloc size
  - `hugetlb.<hugepagesize>.rsvd.max` sets/shows max resv size
  - `hugetlb.<hugepagesize>.events` shows event count
    - failed `hugetlb_cgroup_charge_cgroup` count
  - `hugetlb.<hugepagesize>.events.local` shows non-hierarchical local event count
- `CONFIG_CGROUP_PIDS` regulates task counts (for fork bomb)
  - task subsys calls
    - `cgroup_can_fork -> pids_can_fork` to charge
    - `cgroup_task_release -> pids_release` to uncharge
  - `pids.current` shows current task count
  - `pids.peak` shows historical peak
  - `pids.max` sets/shows max task count
  - `pids.events` shows event count
    - failed `pids_can_fork` count
  - `pids.events.local` shows non-hierarchical local event count
- `CONFIG_CGROUP_RDMA` regulates infiniband rdma
  - infiniband drv calls
    - `rdmacg_register_device` to add infiniband dev
    - `rdmacg_try_charge` to charge
    - `rdmacg_uncharge` to uncharge
- `CONFIG_CGROUP_MISC` regulates misc hw resources
  - subsys calls
    - `misc_cg_set_capacity` to add a res
    - `misc_cg_try_charge` to charge
    - `misc_cg_uncharge` to uncharge
  - `misc.capacity` shows all resources
  - `misc.current` shows current usage per res
  - `misc.peak` shows historical peak per res
  - `misc.max` sets/shows max usage per res
  - `misc.events` shows event count
    - failed `misc_cg_try_charge` attemps
  - `misc.events.local` show local event count
    - non-hierarchical
- `CONFIG_CGROUP_DMEM` regulates device memory (e.g., vram)
  - device driver calls
    - `dmem_cgroup_register_region` to add dmem regions
    - `dmem_cgroup_try_charge` to charge
    - `dmem_cgroup_uncharge` to uncharge
  - `dmem.capacity` shows all dmem regions
  - `dmem.current` shows current usage in each dmem region
  - `dmem.peak` shows historical peak in each dmem region
  - `dmem.{min,low,max}` sets/shows min/low/max
    - `dmem_cgroup_try_charge` never exceeds `dmem.max`
    - when `dmem_cgroup_try_charge` or alloc fails,
      - if `dmem_cgroup_below_low`, it evicts from any cgroup above `dmem.low`
      - if `dmem_cgroup_below_min`, it evicts from any cgroup above `dmem.min`
      - it tries after eviction

## cgroup2 filesystem

- `mkdir $CHILD` calls `cgroup_mkdir`
  - `cgroup_create` creates a new `cgroup`
    - `kernfs_create_dir_ns` creates the dir
  - `css_populate_dir` populates the dir
- `echo +foo > $CHILD/cgroup.subtree_control` calls
  `cgroup_subtree_control_write`
  - it updates `cgrp->subtree_control`
  - `cgroup_apply_control`
    - `cgroup_apply_control_enable`
      - it calls `css_create` on demand for childrend
      - `css_populate_dir` populates the child dirs
- `echo $PID > $CHILD/cgroup.procs` calls `cgroup_procs_write`
  - `cgroup_procs_write_start` returns the task
  - `cgroup_migrate` migrates the task to the new cgroup

## Controller

- a `struct cgroup_subsys` represents a controller
- callbacks
  - hierarchy lifecycle
    - when a controller is enabled for a cgroup, `css_create` calls
      - `ss->css_alloc` to alloc a css
      - `ss->css_online` to enable the css
    - when a controller is disabled for a cgroup, `kill_css` calls
      - `ss->css_offline` to disable the css
      - `ss->css_free` to free the css
  - task migration
    - when a task is migrated to a cgroup, `cgroup_migrate_execute` calls
      - `ss->can_attach` to check
      - `ss->attach` to migrate
  - task lifecycle
    - before a task is forked, `cgroup_can_fork` calls
      - `ss->can_fork` to check
    - after a task is forked, `cgroup_post_fork` calls
      - `ss->fork` to check
    - after a task exits, `cgroup_task_exit` calls
      - `ss->exit` to exit
    - after a task is released, `cgroup_task_release` calls
      - `ss->release` to release
- `CONFIG_CGROUP_PIDS`
  - `pids_css_alloc` allocs a `pids_cgroup`
  - `pids_css_free` frees the `pids_cgroup`
  - `pids_can_attach`
    - `pids_charge` increments the new css recursively
    - `pids_uncharge` decrements the old css recursively
  - `pids_cancel_attach` is the opposite of `pids_can_attach`
  - `pids_can_fork`
    - `pids_try_charge` tries to increment the css recursively
  - `pids_cancel_fork` calls `pids_uncharge`
  - `pids_release` also calls `pids_uncharge`
